Venus driver fixes (source/patches/)
- 0001-venus-hfi_parser-fix-payload-size.patch: upstream Cc:stable payload-size fixes
  (a51cea23e409, bd595b745eb7) that were missing from 6.18.49; without them the firmware
  response buffer is mis-parsed and every HFI session dies.
- 0002-venus-hfi1xx-encoder-fixes.patch: HFI 1xx (msm8916) fixes on top of v6.18.49:
  * do not send HFI_PROPERTY_PARAM_VENC_H264_TRANSFORM_8X8 on 1xx/3xx -- the 1xx/3xx packet
    builders return -EINVAL, which aborts venc session init and made REQBUFS fail on /dev/videoN.
  * keep the H.264/HEVC sequence header in-band on 1xx: the firmware has no separate
    codec-config buffer path and mainline never maps V4L2_BUF_FLAG_CODECCONFIG, so HEADER_MODE_SEPARATE
    (which ffmpeg forces) produced a bitstream with no SPS/PPS.
  * vdec G_FMT: wait up to 100ms for the source-change reconfig before returning -EINVAL, so
    ffmpeg's v4l2m2m decoder (which calls G_FMT right after STREAMON) does not stop at 0 frames.
  * venc: advertise the real 128x32 input alignment through ENUM_FRAMESIZES instead of the
    firmware's nominal step of 1, and round min/max to the same step.  The driver already
    enforced 128x32 in TRY_FMT/S_FMT (upstream does too) but clients could not discover it,
    so a spec-following client would ask for 1280x720 and get a silent mismatch.  Same fix
    cedrus applied for H616/H618 (patches 0008/0009 there): make the constraint visible
    rather than rejecting the request.

Alignment contract (encoder input, msm8916/HFI 1xx)
- width rounds up to 128, height to 32; S_FMT readback is authoritative
  (720 -> 736, 1080 -> 1088, 999 -> 1024, 64 -> 128).
- Decoding needs no padding: vdec_try_fmt_common() aligns only the capture (picture)
  geometry and keeps the coded/output geometry as the bitstream's own, which is the
  correct V4L2 rule (coded format is the picture's own size).
- ffmpeg's v4l2m2m *encoder* still does not copy the driver-adjusted size back into
  avctx, so a non-aligned request crashes that client (userspace SIGSEGV, kernel clean).
  Pad on the command line: -vf "scale=1280:736,format=nv12".

Venus usage constraints (measured on UFI103s, 2026-09-11)
- Encoder geometry: HEIGHT MUST BE A MULTIPLE OF 32. 640x480, 1280x704,
  1280x736 and 1920x1088 encode fine; the common streaming sizes 1280x720 and
  1920x1080 make ffmpeg's v4l2m2m encoder segfault (userspace crash only -- the
  kernel stays clean and the device stays up). Pad instead:
    -vf "scale=1280:736,format=nv12"   (720p)
    -vf "scale=1920:1088,format=nv12"  (1080p)
  Width is aligned by the driver to 128 and tolerated; a height of 720/1080 is
  what breaks, because ffmpeg does not read back the size the driver adjusted.
- Decoding needs `-fps_mode passthrough`: the m2m driver reports timestamp 0 for
  every frame, so the default vsync drops all but a few.
- Use the stable names /dev/video-encoder and /dev/video-decoder; /dev/videoN
  numbers swap between boots (see 70-venus-video.rules).
- Streaming works: FLV/RTMP, MPEG-TS and HLS containers all verified, and a
  30s sustained 720p->736 encode runs in real time (~31s) at 46->57C with no
  kernel errors. Concurrent hardware encode+decode also works.
- RAM is only 376MB. One 720p stream is fine; multiple high-resolution sessions
  cause memory pressure (kswapd order-0 allocation failures were observed).
  Give any long-running streaming service Restart=always so a client-side crash
  (e.g. the non-aligned geometry case) does not leave it dead.
- Recommended one-liner:
    ffmpeg -re -f lavfi -i testsrc=size=1280x720:rate=30 \
      -vf "scale=1280:736,format=nv12" -pix_fmt nv12 \
      -c:v h264_v4l2m2m -b:v 4M -g 30 -f flv rtmp://HOST/app/key

Venus codec capability and transcode (measured 2026-09-11)

Decode (hardware, Venus 1.8): H.264, VP8, VC-1 (G/L), MPEG-4, MPEG-2, H.263, Xvid.
  NO H.265/HEVC and NO VP9 -- both are rejected by the firmware capability mask
  (core->dec_codecs via venus_helper_check_codec()), not by missing driver code.
  H.265 input can only be decoded in software on the CPU.
Encode (hardware): H.264, VP8, MPEG-4, H.263.  No HEVC encoder.

1080p -> 720p transcode, measured on a 300-frame 1080p@30 clip:
  * Hardware H.264 decode           ~47 fps
  * Software H.264 decode           ~78 fps
  * Software H.265 decode           ~45 fps
  * Hardware 720p736 encode          ~49-61 fps
  * Software scale 1080p->720p736    ~23-32 fps  <-- the real bottleneck
  * FULL pipeline, H.264 source      ~32-38 fps  -> real-time OK
  * FULL pipeline, H.265 1080p src   ~23 fps     -> NOT real-time
  * FULL pipeline, H.265 720p src    ~47 fps     -> real-time OK

Rules that make it work:
  1. DECODE IN SOFTWARE, ENCODE IN HARDWARE.  Driving v4l2m2m decode and
     v4l2m2m encode in the SAME ffmpeg process truncates the output to one
     frame, at every resolution tested (640x480 too).  Two separate processes
     piped together also mis-sized frames.  Software decode is fast enough.
  2. Use fast_bilinear for the scale; the default bilinear scaler is ~23fps and
     drags the whole pipeline below real-time.
     -vf "scale=1280:720:flags=fast_bilinear,pad=1280:736:0:8,format=nv12"
  3. Height must be 32-aligned for the encoder, hence 720 -> pad to 736.
  4. -fps_mode passthrough is mandatory (encoder timestamps are all 0).
  5. The encoder cannot downscale: asking for a 720p capture while feeding
     1080p on the output queue silently produces 1920x1088 output, so the
     scaling has to happen in the filter graph.
Ready-made helper: /usr/local/sbin/venus-transcode.sh (tools/venus-transcode.sh)
  venus-transcode.sh <input|URL> [rtmp://... | file.flv | -]
  Recommended wrapper settings: Restart=always, RestartSec=5.

System limits worth knowing:
  * RAM is 376MB.  RTP/TS buffering plus swscale is comfortable for one 720p
    stream; a second high-resolution session risks kswapd allocation failures.
  * /tmp is a 189MB tmpfs -- do not use it for multi-hundred-MB intermediates;
    a full tmpfs silently produces truncated/zeroed writes.
  * CPU tops out at 998.4MHz (four A53s); frequency scaling does not rescue the
    H.265-1080p case (measured ~23-29fps at both 800MHz and 998.4MHz).

CPU overclock (validated on device 2026-09-11)

Mechanism: each A53 core is bound to a SAW2 AVS controller that sets the core
voltage itself on every frequency change, so the CPU OPP nodes carry only
opp-hz -- no opp-microvolt is needed or available.  The A53 PLL driver reads the
DT `cpu_opp_table` (qcom_a53pll_get_freq_tbl -> devm_pm_opp_of_add_table), so
adding OPP nodes really does widen the usable PLL menu.  Hardware PLL rates:
998.4 / 1094.4 / 1152 / 1209.6 / 1248 / 1363.2 / 1401.6 MHz.

Boot variant: release/kernels/ufi103s-ufi003/boot-venus-oc12.img
  DTS: msm8916-handsome-openstick-ufi103s-venus-oc12.dts (Venus + 3 extra OPPs)
  Adds 1094.4 / 1152 / 1209.6 MHz.  Live FDT then exposes seven OPPs and the
  default schedutil policy maxes out at 1209.6 MHz.
  boot sha256 7b669f79aca2bec70ff6a5752e69082f0667b3a44158190a0400ebb8c3deadc1

Measured results (1080p H.264 -> 720p736 transcode of a 300-frame clip):
  998.4 MHz  40.0 fps
  1094.4 MHz 42.9 fps
  1152 MHz   44.8 fps
  1209.6 MHz 46.8 fps      (+17% over the stock maximum)
Each step also passed 60 s all-core load with zero faults: no rcu stall, no
oops, remoteproc0/1 stayed `running`, wlan0 stayed up.

Two safety mechanisms observed working:
  * CPU thermal zone trips passive cooling at 75 C; under sustained all-core
    load the frequency falls back to 800/400 MHz by itself.  Peaks seen were
    74-76 C, well below the 110 C critical trip.
  * No hardware voltage change happens: pm8916_s3 is fixed at 1.30 V (1.35 V
    cap) and SAW2 keeps the core inside it.  This is why the OC is safe-ish --
    it is bounded by the stock rail, not by a driver-supplied voltage.

Writing boot from the running system (no 9008 needed):
  /dev/mmcblk0p12 is the boot partition and is not mounted while running, so
  `dd if=<image> of=/dev/mmcblk0p12 bs=4M conv=fsync` then a read-back `cmp`
  works; a reboot puts the device back if the image is bad (watchdog + pwrkey
  also available).  Archive the partition first.

Rollback: boot-venus.img (boot sha f48a9080...) is the validated non-OC image;
an archive of the pre-OC partition is kept at /root/boot-backup-pre-oc12.img on
the device (sha 2b875a34...).

rmtfs startup fix (found during this work)
  rmtfs.service depended on the systemd .device unit for qcom_rmtfs_mem1, but
  that node is created by the rmtfs_mem module and the unit is not reliably
  active at boot -- rmtfs was silently skipped and the modem remoteproc stayed
  offline.  Fixed with a udev rule (ACTION=="add", SUBSYSTEM=="rmtfs",
  ENV{SYSTEMD_WANTS}+="rmtfs.service") plus a bounded ExecStartPre retry.
  Verified across a reboot: rmtfs active, remoteproc0/1 running.

CPU undervolting: NOT POSSIBLE on this board (investigated 2026-09-11)

The voltage is owned by firmware and there is no data to tune, so this is
blocked by design rather than by missing effort:
  * CPU nodes in msm8916.dtsi have NO `cpu-supply`, so cpufreq-dt never touches
    voltage.
  * The per-core ACC and SAW2 nodes are `status = "reserved"` with the comment
    "Controlled by PSCI firmware" -- Linux is explicitly told not to manage them.
  * No OPP anywhere carries `opp-microvolt`; there is no per-opp voltage table.
  * pm8916_s3 (the L2/APC-side rail, "Needed for L2") is `regulator-always-on`
    and fixed at 1.30 V; writing /sys/class/regulator/*/microvolts is denied.
  * There is no power/current sensor and the SPMI ADC exposes only USBIN, VSYS,
    VDD_VADC, GND_REF and the internal references -- the CPU rail is not even
    observable, so no effect could be measured.
Reaching CPU voltage would need raw PMIC/SPM register writes (devmem or Firehose
pokes), which the project's safety rules forbid, and there is no speed-bin
voltage data to pick safe values from.  H618's lesson applies in reverse here:
do not touch a rail you cannot observe.

The legitimate power/heat lever is FREQUENCY.  Measured tradeoff on the
1080p H.264 -> 720p736 transcode (300 frames, cool start, 3 reps each):
    400 MHz   ~18.8 fps   sustained all-core 53 C
    800 MHz   ~34.9 fps   sustained all-core 64 C
    998.4 MHz ~41.3 fps   sustained all-core 68 C
   1209.6 MHz ~46.9 fps   sustained all-core 73 C
Real time needs 30 fps, so capping at 800-998.4 MHz keeps 1080p->720p real-time
while running ~9-12 C cooler.  Use tools/cpu-power-tradeoff.sh to re-measure.

CPU frequency table: 7 coarse steps, pure DTS (2026-09-11)

Final choice: one step per ~100 MHz, and every included rate already exists in
the upstream a53pll table -- so this variant needs NO kernel change at all, only
the DTS.

  release/kernels/ufi103s-ufi003/boot-venus-oc-100.img
  DTS: msm8916-handsome-openstick-ufi103s-venus-oc-100.dts
  boot sha256 4d96ec8d7e8d86d56a46c67bb5ed657bdd67441e3aabb6cbc4ed728d3389b698

  table:  200 / 400 / 800 / 998.4 / 1094.4 / 1209.6 / 1401.6 MHz
  steps:  96 / 115.2 / 192 MHz above 800 MHz

  1300 MHz is deliberately SKIPPED: its nearest stock rate would be 1305.6 MHz
  (L=68), which upstream a53pll does not list, so including it would have
  required patching the built-in clock driver.  Dropping it keeps the variant
  DTS-only, which is why no 0003 patch exists any more.

  CPU passive-cooling trip 85 C, critical 110 C.
  Verified: all 7 steps move the real a53pll clock (tools/cpu-freq-verify.sh,
  0 mismatches, 0 clock errors); 30 s all-core at 1401.6 MHz peaked at 69 C with
  0 faults; codec regression PASS; 1080p->720p transcode real time; all services
  active.

Why the reachable set is what it is: the list of usable rates comes from the
STATIC table inside drivers/clk/qcom/a53-pll.c, not from the DTS.  Clock tree:
a53pll (XO*L, XO=19.2 MHz) and gpll0 (800 MHz aux) feed a53mux, a mux+divider
whose output is parent*2/(N+1).  A DTS OPP can only select a rate that table
already contains.  Two behaviours that look like faults but are normal:
  * find_freq() rounds a request UP to the next table entry, so an unlisted rate
    resolves to the next listed one (1000 MHz -> 1017.6 MHz).
  * For 200/400/800 MHz the output comes from gpll0 through the mux divider, so
    the a53pll stays parked high; a53pll=1401.6MHz with cpu=800MHz is expected.

GPU frequency is NOT controllable on this SoC: msm8916 has no mainline GPU clock
driver, and the GPU domain hangs off CX/MX -- the same voltage that cannot be
changed.  The GPU OPP in msm8916.dtsi belongs to GPU drivers that do not exist
for this SoC in mainline.

LED status research (2026-09-12, revised to a load gear)
- Hardware inventory on the running UFI103s confirms three usable gpio-leds:
  red:heartbeat (GPIO22), blue:wlan (GPIO20), and green:wan (GPIO21). All are
  GPIO_ACTIVE_HIGH with max_brightness=1; there is no analog brightness control.
- Software PWM for the over-bright red lamp was TRIED AND REJECTED. The kernel
  blink timer arms once per transition and every GPIO toggle pulls the CPU out of
  cpu-sleep-0 (measured with cpuidle state1 usage): 4 ms/16 ms => 100 toggles/s
  => +101 deep-idle exits per second (13118 vs 3007 per 100 s). That is real
  idle-power cost for a cosmetic effect.
- Red is therefore a LOAD GEAR, DC only, never on a timer:
    red DC on  when aggregate CPU utilisation >= 70%
    red DC off when it falls below 65%
  The 65% release point is hysteresis, so the lamp cannot chatter around the
  trip.  It is a "system is working hard" lamp, not an "all is well" lamp.
- Blue is Wi-Fi state: solid = carrier + default IPv4 route (or wpa_cli
  COMPLETED when present), slow = no link / not configured, fast = associating.
- Green is ModemManager state: solid = connected data session, fast =
  connecting/disconnecting, slow = registered-but-not-yet-connected or
  searching/enabled, off = SIM missing/locked or no usable modem.  Idle steady
  state with no SIM is therefore red off + blue solid + green off, which arms no
  timer at all.
- ufi-led-state.service is a persistent monitor (Restart=always) that samples CPU
  every 3 s and the wifi/modem state every 60 s.  The script stays plain POSIX sh
  (sh + cat + grep + awk); no fork-avoidance or timer tricks are used.
- Venus test hooks still exist but only override red and expire on their own:
  testing 120 s, pass 15 s, fail 60 s.
- The device at 192.0.2.10 was live-tested: idle modes=off,solid,off; with 4
  busy loops modes=on,solid,off; after the load stopped it returned to
  off,solid,off.  All three LEDs stayed controllable and the service stayed
  active.  The rootfs builder installs the same script and unit; the flashed
  rootfs was not overwritten or reflashed during this research.

debconf frontend noise (2026-09-13, fix in the builder only, not yet deployed)
- Symptom: every apt run on the device prints "debconf: unable to initialize
  frontend: Dialog ... falling back to frontend: Readline ... Teletype".  These
  lines come from the device's own apt (seen installing fastfetch/npm on
  2026-09-13), not from the image build.
- Root cause: Debconf::Config->frontend() resolves in this order --
  $DEBIAN_FRONTEND, then the debconf/frontend question in the database, then the
  built-in default 'dialog'.  The image ships no dialog/whiptail and no
  Term/ReadLine.pm, and the database has debconf/frontend set to Dialog, so the
  fallback chain always runs.  The built-in default being 'dialog' means even a
  clean database would warn.
- Fix (in build-rootfs.sh and tools/build-rootfs-common.sh): seed
  DEBIAN_FRONTEND=noninteractive into /etc/environment, run mmdebstrap with
  DEBIAN_FRONTEND=noninteractive, and add a customize hook that runs
  debconf-set-selections with "debconf debconf/frontend select Noninteractive".
  Verified on the device that `DEBIAN_FRONTEND=noninteractive
  /usr/share/debconf/frontend <script>` produces no warnings at all, whereas the
  unset case reproduces the exact three-line fallback.

WiFi regulatory domain (2026-09-13, fixed in builder AND applied live)
- Symptom: cfg80211 logged "loaded regulatory.db is malformed or signature is
  missing/invalid", `iw reg get` stayed at country 00 (world), and `iw reg set
  CN` was silently ignored.
- Root cause: cfg80211 verifies regulatory.db against certificates built into the
  kernel.  This kernel ships the upstream certs (net/wireless/certs/wens.hex and
  sforshee.hex).  wireless-regdb's postinst registers the Debian-signed variant
  (-debian, signer CN=benh@debian.org) at priority 100 and the upstream variant
  (-upstream, signer CN=wens) at 50, so the default selection fails signature
  verification.  cfg80211 then falls back to the world domain, and because
  regdb_query_database() returns -ENODATA, even user hints are ignored.
- Proof: the two db bodies are byte-identical (sha256

WiFi TX throughput limitation (2026-09-13, root-caused, NOT fixed)
- Measured: device->host TCP ~5-6 Mbit/s and UDP ~8.7 Mbit/s, while
  host->device reaches ~43.6 Mbit/s.  Device CPU stayed at 7-8%, so this is not a
  CPU limit.  Power save on/off made no difference.  Signal -27 dBm, 40MHz.
- During sustained TX the station dump shows tx bitrate pinned at MCS 0
  (13.5 Mbit/s) while rx is MCS 6-7 (135-150 Mbit/s).
- Cause, at code level: the driver sets IEEE80211_HW_HAS_RATE_CONTROL
  (main.c:1431), so rate selection belongs to the firmware.  Every data frame
  sets bd->bd_rate = WCN36XX_BD_RATE_DATA (txrx.c:534) carrying no rate, and the
  firmware TX completion struct wcn36xx_hal_tx_compl_ind_msg carries only a
  `status` field -- no per-packet rate or retry count -- so the driver never
  calls ieee80211_tx_rate_update().  The only real rate signal is the one-shot
  LL_STATS query (wcn36xx_smd_get_stats -> wcn36xx_process_tx_rate), which
  reports MCS 0.  The vendor driver in
  t507-porting/vendor/linux-orangepi has an identical wcn36xx_dxe_tx_ack_ind, so
  this is not a mainline porting gap.
- Possible directions if this is ever pursued (all driver work, not config):
  WCN36XX_HAL_CFG_FIXED_RATE (hal.h:644) is defined but never sent by the
  driver; the firmware also has SET_TX_PER_TRACKING_REQ and TSM_STATS paths.
  Note the device has no serial console currently, so module-change testing
  needs the serial adapter attached first.

Upstream investigation of the TX throughput problem (2026-09-13)
- Fetched current mainline sources (torvalds master, via proxy) for all wcn36xx
  files and diffed against our 6.18.49 tree.  Result: txrx.c, txrx.h and dxe.h
  are byte-identical; main.c/dxe.c/smd.c/hal.h changes are only janitorial
  (kzalloc_obj/kmalloc_flex conversions, typo fixes) plus a chan_surveys
  allocation change and removal of dead update_scan_params code.  There is NO
  upstream work on wcn36xx TX rate, rate control, or throughput.
- Each driver file in our tree traces to the same single commit because the tree
  is a shallow (depth 1) snapshot, so `git log` cannot be used; the plain-file
  diff against upstream master is the reliable comparison.
- lore.kernel.org and patchwork searches for wcn36xx performance/throughput/rate
  found nothing relevant: the only recent activity is CVE/hardening patches
  (firmware-response bounds checks), a use-after-free fix in the TX ack timer
  teardown (Fan Wu, 2026-09-10), device bring-up, and typo fixes.  No one has
  reported the TX MCS0 / upload asymmetry upstream.
- The two firmware config tables in smd.c differ meaningfully: the WCN3620 table
  (which our board uses) sends ENABLE_DYNAMIC_RA_START_RATE = 133 (= 0x80|5,
  i.e. "start rate adaptation at MCS 5"; hal.h documents the encoding) and
  LINK_FAIL_TX_CNT, while the WCN3680 table instead sends DEFAULT_RATE_INDEX_24GHZ.
  The firmware is therefore already told to start high, yet transmits MCS0, so
  the rate decision and any fallback live entirely in the signed firmware blob --
  the host cannot see or steer it.
- There is no host->firmware "set rate" HAL message.  bd_rate in the TX buffer
  descriptor is only a 2-bit frame-class field (DATA/MGMT/CTRL), not a rate.
- CONFIG_WCN36XX_DEBUGFS is not set in our kernel, so the debugfs file that dumps
  the firmware feature-caps bitmap (which would show DOT11AC/RATECTRL support)
  is unavailable; enabling it would need a module rebuild.
- New measurement: 4 parallel upload streams aggregate to only 6.2 Mbit/s, i.e.
  the same as a single stream, so the limit is an aggregate PHY/MAC ceiling, not
  single-flow TCP behaviour.  That is consistent with MCS0 40MHz (~13.5 Mbit/s
  PHY, ~45% MAC efficiency).
- Runtime debug is possible without rebuilding: debug_mask is a writable module
  parameter (main.c:33, mode 0644).  With WCN36XX_DBG_MAC|WCN36XX_DBG_SMD
  (0x404) and WCN36XX_DBG_TX (0x40) enabled while pushing real upload traffic,
  no AMPDU/BA-session log lines are produced, suggesting TX aggregation may not
  be establishing at all -- a more actionable lead than rate adaptation, but not
  yet proven (mac80211 agg_status debugfs is unavailable because
  CONFIG_MAC80211_DEBUGFS is off; dmesg was legitimately empty because the idle
  kernel logged nothing, not because of a logging fault).
- Conclusion: this cannot be fixed from the device or by configuration.  A real
  fix means driver code plus repeated module rebuild/reboot/measure cycles, and
  the device currently has no serial console, so there is no recovery path if a
  transmit-path experiment wedges the firmware.  Attach the serial adapter before
  attempting it.

Serial console and reboot reliability (2026-09-13)
- Console port identity must be re-derived after every re-plug, not assumed.
  The bench CH343 adapter (USB 1a86:55d3, serial REDACTED-SERIAL, USB path 3-2.4.2)
  now binds to cdc_acm and appears as /dev/ttyACM0.  Earlier notes saying
  "/dev/ttyUSB0" were from when ch341-uart bound the same kind of adapter; the
  tty name and even the USB serial number changed after re-plugging.
- Baud is 115200 and the device end runs 115200 on a clean boot: the kernel
  cmdline is `earlycon console=ttyMSM0,115200` and `stty -F /dev/ttyMSM0` shows
  115200.  An earlier reading showed 57600 because the console can be left at a
  lower rate by agetty, which is started as
  `agetty --noreset --noclear --keep-baud 115200,57600,38400,9600 - vt220`:
  --keep-baud keeps whatever rate the port already had instead of forcing the
  first entry.  Setting `stty -F /dev/ttyMSM0 115200` on the device immediately
  made the host decode cleanly at 115200, confirming both ends support it.
  A baud sweep from the host (115200/1500000/921600/9600/57600) is a reliable way
  to identify the port and rate without guessing.
- tools/ufi-console.sh wraps this: `id` reports the resolved port/baud, `read`
  and `send` do bounded console I/O.  SUDO_PW and UFI_CONSOLE_PORT/BAUD are env
  overridable.
- Reboot without the watchdog fix HUNG THE BOARD.  `systemctl reboot` wedged
  after `qcom-wcnss-pil: unexpected response to sysmon event` (remoteproc1/modem
  teardown), then `rcu_preempt detected stalls` repeated forever, and the log
  showed `Failed to set watchdog hardware timeout to 10min: Invalid argument`.
- Root cause of the failed watchdog arm: the PM8916 PON watchdog accepts 1..127 s
  (drivers/watchdog/pm8916_wdt.c: PM8916_WDT_MIN_TIMEOUT=1,
  PM8916_WDT_MAX_TIMEOUT=127; the DTS sets timeout-sec=60 and wdctl confirms 60).
  systemd 257's default RebootWatchdogSec is 10min = 600 s, far outside that
  range, so the arm failed and there was no hardware recovery.
- Fix: /etc/systemd/system.conf.d/10-watchdog.conf with
  RuntimeWatchdogSec=60s and RebootWatchdogSec=60s, then `systemctl daemon-reexec`
  (verified: RebootWatchdogUSec=1min, systemd/PID 1 holds /dev/watchdog0).
  Baked into build-rootfs.sh and tools/build-rootfs-common.sh.
- Watchdog reset VERIFIED on hardware: armed /dev/watchdog0 for 15 s with
  WDIOC_SETTIMEOUT and stopped pinging -> the board dropped off the network after
  ~12 s and was back in ~21 s, with systemd time reset to 1970 (no RTC, i.e. a
  cold reset).  wdctl afterwards reports CARDRESET boot-status = 1, the PMIC's own
  record that the watchdog reset the CPU.  This also means a reset is a CLEAN
  boot, unlike the wedged software reboot.
- Consequence for the WiFi work: the board is now self-recovering from kernel
  hangs (runtime watchdog, 60 s) and its console is reachable at 115200, so a
  wedged transmit-path experiment no longer requires a manual power cycle.  Note
  the console and watchdog are safety nets, not substitutes: a hang still costs
  the running test and ~20 s to reboot.

WiFi TX throughput FIXED (2026-09-14)
- Root cause found and fixed: the wcn36xx firmware config table set
  WCN36XX_HAL_CFG_MAX_MEDIUM_TIME (cfg id 9) to 6000 (us) for the WCN3620 table.
  That value is too small for HT operation: the firmware's rate adaptation
  settles at MCS0 and never leaves it.  Raising it to 20000 makes the link hold
  MCS4-MCS5.  This is a firmware-behaviour knob, not a host-visible rate.
- Measured, single-stream device->host TCP (clean 40 MHz -27 dBm link):
    MAX_MEDIUM_TIME 6000  (old default) :  MCS0  13.5 Mbit/s PHY, ~6 Mbit/s
    MAX_MEDIUM_TIME 8000                :  MCS0, ~6 Mbit/s
    MAX_MEDIUM_TIME 10000               :  MCS4 90 Mbit/s PHY, 43-45 Mbit/s
    MAX_MEDIUM_TIME 12000               :  MCS4, 44-46 Mbit/s
    MAX_MEDIUM_TIME 16000               :  MCS0, ~6 Mbit/s   (non-monotonic!)
    MAX_MEDIUM_TIME 20000 (new default) :  MCS4-MCS5, 44-50 Mbit/s
    MAX_MEDIUM_TIME 30000               :  MCS4, 44-47 Mbit/s
  The response is NOT monotonic (8000 and 16000 fall back to MCS0), so the value
  has to be measured, not derived.  20000 was chosen as the default: it is in the
  group that works and gives the highest PHY rate seen (MCS5 in some runs).
- Verified with the value baked into the driver table and NO module parameters
  set: three consecutive sustained 30 s uploads gave 47 / 45 / 44 Mbit/s at MCS4,
  tx retries 0, tx failed 0, temperature 52 C.  Downlink is unaffected (device RX
  still MCS6-7, 45-50 Mbit/s).  Aggregate across parallel streams matched the
  single-stream figure, consistent with a genuine PHY-rate limit being lifted.
- What did NOT work, and why (all tested, all ineffective for data frames):
  * WCN36XX_HAL_CFG_FIXED_RATE (id 18) only accepts legacy/CCK rates.  Values
    1/2/4 produced 1/2/11 Mbit/s, proving the knob works, but every HT encoding
    (128, 130, 133, 135) left data frames at MCS0 -- the firmware simply will not
    accept a host-specified HT rate.
  * ENABLE_DYNAMIC_RA_START_RATE (id 210) had no effect at 0, 64, 133, 134, 135
    even though the table already sets it to 133 ("start at MCS5").
  * RA_FILTER_ENABLE (194), RA_RATE_LIMIT_INTERVAL (195), MCS_RATES (190),
    RETRYRATE_POLICY (19), FORCE_POLICY_PROTECTION (22) had no effect.
  * TX aggregation is NOT the problem: station agg_status showed TX BA sessions
    up on TID 0/1 throughout, and the mean TX frame size during upload was 1529
    bytes (full MSS), so the path is not fragmenting.
  * The firmware feature-cap bitmap (now readable, see below) contains RATECTRL
    but no BLOCKACK; the driver only uses that list for debug names and SCAN_OFFLOAD
    gating, so it does not gate aggregation.
- Changes made:
  * smd.c: MAX_MEDIUM_TIME 6000 -> 20000 in the WCN3620 table, with a comment
    recording the measurement.  This is the actual fix.
  * main.c / smd.c / wcn36xx.h: a "cfg_override" module parameter that overrides
    any WCN36XX_HAL_CFG_* value in the start-time table, e.g. cfg_override="9=20000".
    Needed because the firmware latches config at MAC start, so a runtime
    update-cfg is accepted but ignored -- changing a value requires a link
    re-start.  This is what made a broad sweep possible without a rebuild per
    value.
  * debug.c / debug.h: a debugfs "cfg" knob (write "<id> <value>", read back the
    last value) for the same purpose, and firmware_feat_caps file mode 0200 ->
    0444.  The file was registered with a read handler but mode 0200 upstream, so
    nobody could ever read the firmware capability list; 0444 fixes that.
  * source/configs/ufi103s-venus.config: CONFIG_DEBUG_FS, CONFIG_CFG80211_DEBUGFS,
    CONFIG_MAC80211_DEBUGFS, CONFIG_WCN36XX_DEBUGFS.
  * source/patches/0003-wcn36xx-fix-tx-throughput-max-medium-time.patch holds the
    whole driver change and was verified to apply cleanly to pristine upstream
    source.
  * tools/wcn36xx-cfg-sweep.sh and tools/wcn36xx-rate-sweep.sh automate the
    set-parameter / re-start-link / measure-throughput loop on the device;
    tools/wifitest.py is the tiny TCP sender they use.
- Build notes for next time: the module had to be rebuilt with `make modules`
  (whole tree), not `make <dir>/`, because the directory target only runs
  checksyscalls and does not relink; and `make M=<dir>` writes objects into the
  SOURCE tree, so avoid that form when O= is in use.  Removing stale .o files by
  hand truncates Module.symvers and causes modpost "undefined!" errors -- rebuild
  with `make modules` to restore it.
- Deployed state: the fix is live on the device (module sha256
  7b6d802cdf2ee12db03a760bb6c19ab56218e11238cbdcb8cb1ee2d5823fe4ff, identical on
  host and device) and the old module is backed up at /root/wifi-mod-backup/.
  The fix is NOT yet in a release rootfs/module image: it lives in the driver
  source plus source/configs and needs a normal variant build to be shipped.
  (An earlier build of this module had sha256 480d1511...; it was rebuilt after
  converting the diagnostic parsing from simple_strtoul to kstrtoul, so only the
  later hash is current.)

Distribution repo for field testing (2026-09-14)
- /opt/helloworld/ufi00x-mainline is a standalone git repo prepared for GitHub,
  holding the WiFi fix, per-board boot images and the tooling to have owners of
  other boards test it.  Four commits so far.
- Why it exists: the fix is confirmed on WCN3620 only.  WCN3660B (ufi001b,
  ufi001c, sp970, uz801) shares the same firmware config table, so results from
  those boards are what would confirm or bound the fix upstream.  WCN3680 uses a
  different table (MAX_MEDIUM_TIME 4096, smaller than the 6000 called "too
  small"), which is why the write-up says the threshold is a property of this
  firmware build rather than a general rule.
- Patches were split by logical change and each verified independently:
  0001 firmware_feat_caps readable (self-contained upstream bug: the file had a
  read handler but mode 0200), 0002 the MAX_MEDIUM_TIME fix, 0003 optional
  cfg_override diagnostics.  0001+0002 reproduce the fix state byte-for-byte.
  All three pass checkpatch --strict with no errors or warnings.
- Board definition provenance: source/dts/* corresponds one-to-one with
  HandsomeMod's patches-5.10/0083-arm64-dts-add-support-for-Handsome-Openstick-Family.patch
  (HandsomeMod fa7f0be, OpenStick 4be50db).  The board layout is inherited from
  that field-tested work; our packaging of it is new.
- Delivery detail worth remembering: the WiFi fix travels in wcn36xx.ko in the
  ROOTFS, never in a boot image (boot images are kernel+DTB only, and wcn36xx is
  modular).  Documented explicitly because it is easy to get wrong.
- EDL (9008) entry, as confirmed on this hardware: hold the reset button (or
  short the reset pad to ground) BEFORE applying USB power, since the boot ROM
  samples the line at power-on.  Do not document GPIO numbers for this: the
  numbers are not visible on the device, only the button/pad is.  Public Firehose
  loaders are rejected by these sticks, so Miko's bundled MSM8916 loader is the
  one to use.
- Flashing is an accepted path in that repo, with a MANDATORY full-eMMC Miko
  backup first: modemst1/modemst2/fsg/fsc hold per-device modem calibration that
  no image can regenerate, so overwriting them ends 4G permanently.  Expected
  backup size 3,909,091,328 bytes (3.64 GiB); the full GPT of this board is
  recorded in docs/backup-and-restore.md.
- IPERF3 was added to PKGS_EXTRA in build-rootfs.sh and
  tools/build-rootfs-common.sh, so the measurement tool used by the repo's test
  script ships in new rootfs images.  The already-released rootfs does not have
  it; the copy on the device was installed by hand earlier.
