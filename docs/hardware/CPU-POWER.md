# CPU 频率、电压与散热（MSM8916 / UFI103s 实测）

一句话：**这台机器的性能旋钮只有频率，没有电压**；频率到 **1209.6 MHz** 之后
再无收益，散热是持续负载的真正天花板。

## 一、频率表（7 档，纯 DTS 改动）

当前 `source/dts/common/msm8916-handsome-openstick-common.dtsi` 暴露：

```
200 / 400 / 800 / 998.4 / 1094.4 / 1152 / 1209.6 MHz
```

**1300 MHz 是刻意跳过的**：最接近的库存频率是 1305.6 MHz（L=68），上游
`drivers/clk/qcom/a53-pll.c` 的静态表里没有，加进来就得打补丁改时钟驱动。
去掉它，这个变体就**只用 DTS**，不需要任何内核改动。

可达频率集合由 `a53-pll.c` 的**静态表**决定，不是 DTS。时钟树：`a53pll`
（XO×L，XO=19.2 MHz）与 `gpll0`（800 MHz 辅助）喂给 `a53mux`，后者是
mux+分频器，输出 = parent×2/(N+1)。**DTS 的 OPP 只能选表里已有的频率。**

两个看起来像故障、其实正常的行为：

- `find_freq()` 把请求**向上**取整到下一个表项（请求 1000 MHz 会得到 1017.6 MHz）。
- 200/400/800 MHz 实际由 `gpll0` 经分频器输出，`a53pll` 会停在高位；
  `a53pll=1401.6MHz` 而 `cpu=800MHz` 属于预期。

验证工具：`tools/cpu-freq-verify.sh`（逐档核对真实 a53pll 时钟，0 误差）。

## 二、实测上限：1209.6 MHz

单线程交错测量（openssl sha256 绑核、libx264 threads=1）：

| 频率 | 吞吐 | 相对收益 |
|---|---|---|
| 998.4 MHz | 64.5k op/s | 基准 |
| 1209.6 MHz | 78.0k op/s | **+21%**（正好等于频率比） |
| 1401.6 MHz | 78.1k op/s | **无收益**（PLL 确实到了 1401.6，debugfs `clk_rate` 已确认） |

转码管线在同一点平台化：1209.6 MHz 43.8 fps vs 1401.6 MHz 44.1 fps。

原因：核心供电轨固定在 **1.30 V**（`pm8916_s3`，上限 1.35 V），提不上去。
1.6 GHz 只会带来热量，不会带来速度。

**所以 1401.6 MHz 不再暴露**（旧运行镜像曾有这一档，已移除）。

### 频率—发热权衡（1080p H.264 → 720p736 转码，300 帧，冷启动，各 3 次）

| 频率 | 帧率 | 全核持续温度 |
|---|---|---|
| 400 MHz | ~18.8 fps | 53 °C |
| 800 MHz | ~34.9 fps | 64 °C |
| 998.4 MHz | ~41.3 fps | 68 °C |
| 1209.6 MHz | ~46.9 fps | 73 °C |

实时需要 30 fps，所以**限在 800–998.4 MHz 仍能保住 1080p→720p 实时，同时低 9–12 °C**。
用 `tools/cpu-power-tradeoff.sh` 重测。

## 三、降压不可行（已定案，不是"还没试"）

电压由固件掌控，且没有可调数据：

- `msm8916.dtsi` 的 CPU 节点**没有 `cpu-supply`**，cpufreq-dt 从不碰电压。
- 每个核的 ACC 与 SAW2 节点是 `status = "reserved"`，注释写明
  "Controlled by PSCI firmware" —— Linux 被明确告知不要管。
- 没有任何 OPP 带 `opp-microvolt`，根本没有 per-opp 电压表。
- `pm8916_s3`（L2/APC 侧供电轨）是 `regulator-always-on`，固定在 1.30 V；
  写 `/sys/class/regulator/*/microvolts` 会被拒绝。
- **没有功率/电流传感器**，SPMI ADC 只暴露 USBIN、VSYS、VDD_VADC、GND_REF
  与内部参考 —— CPU 轨连观测都观测不到，改了也测不出效果。

要碰到 CPU 电压只能做原始 PMIC/SPM 寄存器写（`devmem` 或 Firehose poke），
而工程安全规则禁止这么做；也没有 speed-bin 电压数据可选安全值。
**不要碰你看不见的供电轨。**

## 四、散热与热保护

- CPU 被动冷却的**上游默认是 75 °C**；本项目公共 dtsi 把它改成 **85 °C**
  （critical 保持 110 °C），五个功能变体共用。GPU 被动冷却仍是 75 °C，
  critical 95 °C。
- 实测：全核持续负载下频率会自己退到 800/400 MHz，峰值 74–76 °C。
- **2026-10-10 当前散热条件下**，四核满频 + 96 MiB 内存校验约 **27 秒到 80 °C**，
  被测试保护中止；限 800 MHz 后完成 60 s CPU / 90 s 内存测试，峰值 **75 °C**。
- 1280×736@30 GPU 推流也约 **82 秒到 80 °C**，同样中止。
- 所以**不要宣称默认频率可无限持续满载**；持续负载要先定温度/帧率合同，
  或改善散热。

细节见 `docs/validation/7.2.9.md` 的散热一节。

## 五、GPU 频率不可控

msm8916 在主线**没有 GPU 时钟驱动**，且 GPU 域挂在 CX/MX 上——正是那个改不了
的电压域。`msm8916.dtsi` 里的 GPU OPP 属于主线里并不存在的 GPU 驱动。

## 六、其它系统上限（实测）

| 项 | 值 |
|---|---|
| RAM | 376 MB（可用约 270 MB） |
| CMA | 32 MB（venus 缓冲从此出） |
| `/tmp` | tmpfs，约 189 MB —— 不要放几百 MB 的中间产物，写满会静默截断 |
| 根分区 | 3.3 GB；镜像带 `x-systemd.growfs` 开机自动撑满 |
